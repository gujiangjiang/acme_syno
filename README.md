# Synology acme.sh Auto-Deploy 🚀

这是一个专为群晖 (Synology) NAS 打造的，基于 Docker 版 `acme.sh` 的全自动 SSL 证书申请、续签与部署脚本。

通过将**核心逻辑代码**与**配置变量**彻底分离，并引入智能状态判断、容错回退与自愈同步机制，让群晖的证书管理变得前所未有的安全、简单和健壮。

## ✨ 核心特性

- **代码与配置完全分离**：主逻辑脚本 (`acme.sh`) 与配置文件 (`config.conf`) 物理隔离。更新脚本不再担心配置丢失，配置敏感信息也可独立设置严格的读写权限以确保安全。
- **智能自适应 Issue / Renew**：告别无脑 `--issue` 导致的强制覆盖报错死循环。脚本会自动检查内部记录，无记录则全新申请，有记录则智能续签并由 acme.sh 自动接管 30 天续期判定。
- **自愈式部署同步 (Self-Healing Deploy)**：脚本在“未到续签期”时，会自动比对「容器内证书」与「群晖已部署证书」的 SHA256 指纹。一旦发现两者不一致（例如容器后台定时任务已抢先续签、或上次部署失败），立即自动补发部署，确保群晖永远用上最新证书；同时避免每次运行都无谓地重复替换证书、重载网页服务。
- **双模式部署策略**：通过 `config.conf` 中的 `DEPLOY_MODE` 自由切换——`smart`（智能比对、按需部署，推荐）或 `always`（每次运行强制部署，最保险）。
- **证书状态自检**：每次运行结束都会输出证书的真实到期时间，并对“剩余不足 30 天”的情况给出醒目的临期警告，让隐患无处遁形。
- **环境预检防患于未然 (Pre-flight Check)**：脚本执行前自动检测指定的 Docker 容器是否处于运行状态，防止产生冗长复杂的底层报错。
- **智能路径容错回退 (Graceful Fallback)**：极具鲁棒性的寻址机制。优先寻找 `config/config.conf`，若缺失则自动回退寻找同级目录的 `config.conf`，并输出友好的容错日志。
- **原生支持多域名复用**：只需维护一份核心代码！通过传入不同的配置文件参数，即可在群晖计划任务中无限扩展多域名管理，日志集中统一。

## 📂 推荐目录结构

建议在群晖中建立如下结构（例如放在 `/volume1/docker/acme.sh/auto/` 下）：

```text
auto/
 ├── acme.sh           <-- 永远不需要再改动的核心脚本
 ├── acmelog.txt       <-- 所有的运行日志统一输出到此处
 └── config/           <-- 专门存放配置文件的文件夹 (推荐)
      ├── config.conf
      ├── config_aaa.conf
      └── config_bbb.conf
```

## 🛠️ 前置准备

1. 确保群晖上已安装 Docker (Container Manager)。
2. 确保群晖后台已经有一个名为 `acme.sh` (可在配置文件中自定义) 的守护型容器正在常驻运行。
3. 你的群晖账户具备修改证书的权限。

## 🚀 快速上手

### 1. 准备配置文件
将本项目中的 `config.conf` 模板放入 `config` 文件夹中。
根据文件内的详尽注释，填入你的：
- Docker 容器名称 (`ACME_CONTAINER_NAME`)
- 域名 (`DOMAIN`)
- DNS 服务商 API Token (如 Cloudflare, DNSPod, 阿里云)
- 群晖账号、密码、Device_ID 等部署信息
- 部署策略 (`DEPLOY_MODE`，默认 `smart` 即可，追求绝对保险可改为 `always`)

### 2. 在群晖中设置计划任务
登录群晖 DSM：**控制面板 -> 任务计划 -> 新增 -> 计划的任务 -> 用户定义的脚本**。
建议将运行频率设置为：**每月运行一次**（例如每月 1 日凌晨 2 点）。

证书有效期 90 天、到期前约 30 天才进入续签窗口，每月检查一次绰绰有余；且 acme.sh 容器自带的后台定时任务（每 6 小时一次）会在容器内兜底完成续签，脚本每次运行都会自动比对并同步部署到群晖，完全无需更频繁地运行。

> 注意：不建议停用容器自带的后台定时任务；若因特殊原因确要停用，请将运行频率改为每周一次，以免极端情况下续签窗口与月度运行错位。

在“任务设置” -> “运行命令”面板中，根据你的使用场景填入以下命令：

#### 场景一：单域名默认执行
如果不加任何参数，脚本会自动去 `config` 文件夹下寻找 `config.conf`，找不到则回退寻找脚本同目录下的 `config.conf`。
```bash
bash /volume1/docker/acme.sh/auto/acme.sh >>/volume1/docker/acme.sh/auto/acmelog.txt 2>&1
```

#### 场景二：多域名复用执行 (高级)
如果你有多个域名，请在 `config` 文件夹下复制多份配置文件（如 `config_aaa.conf`, `config_bbb.conf`），在计划任务中分多行执行并指定配置文件的绝对路径：
```bash
bash /volume1/docker/acme.sh/auto/acme.sh /volume1/docker/acme.sh/auto/config/config_aaa.conf >>/volume1/docker/acme.sh/auto/acmelog.txt 2>&1
bash /volume1/docker/acme.sh/auto/acme.sh /volume1/docker/acme.sh/auto/config/config_bbb.conf >>/volume1/docker/acme.sh/auto/acmelog.txt 2>&1
```

## 📝 日志查看

得益于详尽的日志输出设计，你可以随时打开 `acmelog.txt` 像看流水账一样查看任务执行情况：
- 所有时间戳格式均已统一为与 acme.sh 一致的本地时间样式（脚本会自动探测群晖时区并同步给容器，不再出现 UTC 与本地时间混排的“时间穿越”现象）；
- 每次运行结束都会输出“🕒 容器内当前证书到期时间: ...”，**请留意这一行**，它就是当前证书的真实有效期；
- 如果证书尚未到续签期，脚本会自动校验“群晖已部署证书”与“容器内证书”的 SHA256 指纹：一致则安静退出（“✅ 校验通过”）；不一致则自动补发部署（“⚠️ 检测到群晖当前证书与容器内证书不一致…”）；
- 如果发生了路径容错，你将看到：“⚠️ 提示: 未在 config 目录找到配置文件，已智能回退...”
- 如果容器没有启动，你将看到：“❌ 致命错误: 找不到名为 'acme.sh' 的容器...”

## ⚠️ 常见问题
**Q: 执行后提示需要 `--force` 或 `--renew`，并且报错退出了？**
A: 本脚本已经彻底重构了判断逻辑，极大概率不会出现此问题。如果你是从旧版本脚本迁移过来的，通常是因为之前错误操作遗留了废弃的域名文件夹。请手动进入 Docker 容器，执行 `--remove -d 你的域名` 彻底清除旧记录后再次运行本脚本即可。

**Q: 群晖里的证书都过期了，任务日志却一直提示“跳过更新 / 无需操作”？**
A: 这是旧版脚本的隐性缺陷，也是本项目诞生的“血泪教训”：
1. acme.sh 官方 Docker 镜像以 daemon 模式运行时自带后台定时任务（默认每 6 小时执行一次 `--cron`），证书会在容器内部自动续签；
2. 但容器内部没有群晖账号等部署信息，续签出来的新证书不会自动部署到群晖；
3. 旧版脚本在“未到续签期”时会直接退出，也不执行部署——于是群晖一直停留在旧证书上，直到过期。

新版脚本已彻底修复：脚本每次运行都会比对「容器内证书」与「群晖已部署证书」的 SHA256 指纹，只要发现不一致就自动补发部署，并对证书剩余有效期做兜底检查。升级脚本后手动运行一次任务，即可立即把容器里已续签的有效证书部署到群晖，恢复正常。

**Q: 部署时报错 `error code: 6`（无法解析主机名）或 `Unable to authenticate to http://xxx:5000`？**
A: 旧版脚本传递部署变量时使用了大小写混合的名字（如 `SYNO_Hostname`），而 acme.sh 3.x 的 `synology_dsm` 部署钩子只读取**全大写**的 `SYNO_*` 变量（如 `SYNO_HOSTNAME`），读取不到时就会回退使用很早以前持久化在 acme.sh 域名配置里的旧地址（例如某个早已失效的旧域名），这就是报错里出现陌生主机名、且 config.conf 修改似乎"不生效"的原因。

新版脚本已修复：新旧两套变量名同时传递、显式传入默认值并自动覆盖旧值，同时增加了部署前的连通性预检提示。更新脚本后重新运行即可恢复正常。

若更新后仍提示“无法连接”，说明容器没有使用 host 网络，请将 `SYNO_Hostname` 改为群晖的局域网 IP（可用 `docker inspect acme.sh -f '{{.HostConfig.NetworkMode}}'` 查看容器的网络模式）。

**Q: acme.sh 的内部日志（容器内 `/acme.sh/acme.sh.log`）为什么会疯涨到几万行？**
A: 属于正常现象，来源主要有两处：
1. 官方镜像 daemon 模式自带的后台定时任务每 6 小时执行一次 `acme.sh --cron`（含自我升级检查），每次都会写入详细日志；
2. 本脚本执行申请/续签时带 `--log` 参数，同样会追加写入。

运行几个月后累积到数万行并不影响功能，建议定期清空即可：

```bash
docker exec acme.sh sh -c ': > /acme.sh/acme.sh.log'
```

（进阶）后台定时任务的时间表保存在容器卷的 `/acme.sh/crontab` 文件中，如确有需要可自行调整频率；删除该文件后重启容器会自动重新生成。
